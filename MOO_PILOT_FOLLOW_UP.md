# MOO — follow-up план офлайн-пилота

**Цель:** довести текущую версию до контролируемого тестирования с одним готовым рестораном, не включая неподтверждённые функции в публичный scope.

## 1. Пилотная конфигурация

| Параметр | Решение для первого пилота |
|---|---|
| Рестораны | 1 активный ресторан |
| Telegram | 1 bot + 1 Mini App URL + настроенный webhook |
| Tenant mode | Single-tenant, но с обязательной проверкой restaurant context |
| Каталог | Реальное меню ресторана; магазин включать только при необходимости |
| Fulfilment | Delivery с зонами; pickup включать только если ресторан его реально использует |
| Оплата | Один проверенный метод: QR с ручным подтверждением либо другой согласованный метод |
| Подписки | Выключены в основном пилоте или включены отдельным beta-сценарием после приёмки |
| CRM | Визиты и ручные Telegram-сценарии; массовые автоматические рассылки не включать до anti-spam |
| Поддержка | Один product owner, один технический ответственный, один ответственный со стороны ресторана |

## 2. План работ

### Этап 0. Фиксация scope и исходных данных — 0,5–1 день

Владелец продукта должен утвердить ресторан, валюту, часы работы, зоны доставки, минимальный чек, стоимость доставки, способы оплаты, статусы заказа и список ролей. От ресторана нужны меню в согласованном формате, фотографии, цены, правила стоп-листа, Telegram username владельца и список сотрудников.

**Результат:** подписанный pilot charter, source-of-truth файл меню, таблица ролей и заполненная матрица environment variables.

### Этап 1. Production hardening — 1–2 дня

Нужно настроить и проверить production DB, Prisma schema/migrations, Telegram webhook, `APP_URL`/`NEXTAUTH_URL`, bot token, storage для изображений, payment secrets и URL callback/webhook. Следует проверить, что несуществующий или устаревший restaurant ID не приводит к доступу к неправильному ресторану. На этом этапе также необходимо зафиксировать commit/version и создать backup БД.

**Результат:** staging/prod окружение с health-check, version endpoint, webhook status и документированной процедурой rollback.

### Этап 2. Настройка ресторана — 1 день

Загрузить меню и изображения, проверить категории, modifiers, цены и доступность. Настроить баннеры, часы работы, delivery zones, payment method, текст уведомлений и пользователей команды. Провести визуальный проход на мобильном Telegram viewport.

**Результат:** ресторан может самостоятельно открыть/закрыть приём заказов и изменить базовые операционные настройки.

### Этап 3. Приёмочные сценарии — 1–2 дня

Прогнать сценарии ниже с реальными аккаунтами Telegram и зафиксировать фактический результат, timestamp, order ID и скриншот/лог только там, где это нужно. Каждый failed сценарий получает severity, владельца и срок исправления.

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| AT-01 | `/start` в Telegram | Гость получает кнопку открытия Mini App |
| AT-02 | Первый вход гостя | Авторизация проходит без пароля, показывается правильный ресторан |
| AT-03 | Меню | Категории, фото, цены, доступность и modifiers совпадают с исходным файлом |
| AT-04 | Корзина | Добавление, изменение количества, удаление и итоговая сумма работают после refresh |
| AT-05 | Delivery quote | Адрес в зоне даёт корректные fee/window; адрес вне зоны отклоняется |
| AT-06 | Pickup | Если включён, не требует delivery address и не добавляет delivery fee |
| AT-07 | Checkout | Сервер пересчитывает позиции и сумму; подмена client total отклоняется |
| AT-08 | Double submit | Двойной tap/refresh не создаёт два заказа при наличии client request ID |
| AT-09 | Payment happy path | Платёж/чек попадает в понятный оператору статус |
| AT-10 | Payment reject | Оператор может отклонить/попросить повтор; заказ не зависает без владельца |
| AT-11 | Owner order flow | OWNER/ADMIN видит заказ и может выполнить разрешённые переходы |
| AT-12 | Kitchen/courier flow | Операционная роль видит только нужные действия и не получает лишний доступ |
| AT-13 | Customer notifications | Гость получает уведомления о принятии и изменении статуса |
| AT-14 | Stop-list | Недоступная позиция не оформляется даже при устаревшей корзине |
| AT-15 | Closing | Закрытие ресторана блокирует новый заказ предсказуемым сообщением |
| AT-16 | Backup restore | Резервная копия восстанавливается на отдельную БД, данные проверены |

### Этап 4. Shadow mode — 1–2 дня

В первые часы ресторан принимает ограниченное число заказов через MOO параллельно с привычным каналом. Команда не масштабирует трафик, а наблюдает: время до подтверждения, ошибки оплаты, ошибки адресов, задержки уведомлений, ручные корректировки и случаи, когда оператор обходил систему.

**Результат:** список реальных operational gaps, а не только багов интерфейса.

### Этап 5. Ограниченный live pilot — 3–7 дней

Открыть MOO для заранее выбранной аудитории: сотрудники, постоянные гости и QR-код в ресторане. Ежедневно проводить короткий review заказов, инцидентов и обратной связи. Не включать массовые кампании, пока не подтверждены consent, cooldown, daily cap и способ остановки рассылки.

## 3. Backlog с приоритетами

| Приоритет | Работа | Owner | Definition of Done |

| P0 | Role matrix | Product/Tech | OWNER/ADMIN/STAFF/операционные роли проверены отрицательными тестами |
| P0 | DB backup/restore | Ops | Restore drill завершён с измеренным RTO/RPO |
| P0 | Incident runbook | Product/Tech | Есть escalation, manual fallback и support contact |
| P1 | Menu data acceptance | Restaurant/Product | Меню и фото сверены с source of truth |
| P1 | Stop-list UX | Tech/Product | Позиция одинаково недоступна в UI, API и checkout |
| P1 | Status transition rules | Tech | Нельзя выполнить запрещённый переход; все изменения логируются |
| P1 | Notification dedupe | Tech | Повторный event не создаёт неконтролируемый дубль |
| P1 | Observability | Tech | Ошибки API/client/webhook видны с correlation/order ID |

## 4. Ежедневный пилотный dashboard

| Метрика | Как считать | Сигнал тревоги |
|---|---|---|
| Заказы | Создано, подтверждено, отменено, доставлено | Растёт доля отмен или заказов без владельца |
| Conversion | Mini App sessions → checkout → order | Резкое падение между checkout и order |
| Payment success | Успешно подтверждённые / созданные платежи | Есть заказы в pending сверх операционного SLA |
| Time to accept | Created → Confirmed | Превышает согласованный SLA ресторана |
| Time to fulfil | Confirmed → Delivered/Pickup complete | Растёт относительно часов пик |
| Notification delivery | Отправлено/ошибка/дубликат | Ошибки Telegram или повторные сообщения |
| Menu integrity | Ошибки цены, missing image, unavailable item | Любая ошибка по цене или оформление stop-listed item |
| Support load | Инциденты по категориям | Повторяется один и тот же обходной процесс |

## 5. Follow-up после пилота

Через 24 часа после старта необходимо провести короткий разбор с рестораном, а через 3–7 дней — итоговый review. Для каждого инцидента фиксируются дата, ресторан, роль пользователя, order ID, шаг сценария, фактический результат, ожидаемый результат, severity, workaround и решение. Отдельно собираются запросы, которые выглядят как «новая функция», чтобы не смешивать их с defect и configuration gap.

### Шаблон follow-up отчета

| Раздел | Что записать |
|---|---|
| Период | Дата, часы работы и версия commit |
| Объём | Сессии, заказы, delivery/pickup, способы оплаты |
| Надёжность | Ошибки API, webhook, payment, client errors |
| Операции | Среднее время подтверждения и выполнения |
| Пользователи | Что было непонятно гостю и сотрудникам |
| Деньги | Суммы заказов, fee, refunds/ручные корректировки |
| Решение | Продолжать, ограничить, остановить или расширить |
| Backlog | Defects, configuration tasks, product requests |

## 6. Условия расширения после пилота

Переход к нескольким ресторанам возможен только после того, как один ресторан прошёл не менее нескольких рабочих дней без P0-инцидентов, восстановление БД проверено, роли и tenant isolation доказаны отрицательными тестами, а ресторан способен самостоятельно менять меню, цены, часы и зоны доставки. Подписки и массовый маркетинг следует включать отдельными release gates, потому что они увеличивают финансовый, коммуникационный и операционный риск.

**Итоговый порядок:** сначала доказать заказ и операционную обработку, затем стабилизировать оплату и уведомления, после этого включать CRM-автоматизацию, и только потом масштабировать B2B и подписки.
